## 🔒 Security & Auth Evidence (detailed)

1. **Privilege escalation, verified source-reading:** `app/api/user/update-role/route.ts` — no `auth()`, takes `{userId, role}` and calls `clerk.users.updateUserMetadata(... publicMetadata: {role})`. `app/api/admin/users` GET returns full Clerk user list; POST mutates roles gated only by the client page.
2. **Public-middleware API convention:** `middleware.ts:10` `/api/(.*)` in `isPublicRoute` → 156 routes ship unauth by default; only 47 self-gate. `proxy.ts` is dead (Next 15 ignores it) but is *installed* with a different matcher.
3. **Duplicates in served headers:** `middleware.ts:48-50` fake rate-limit (always `100/99`), `:53-55` dead static-cache branch.
4. **Secret/key exposure:** env sanity — all secret material is correctly server-only (`SUPABASE_SERVICE_ROLE_KEY`, `VAPID_PRIVATE_KEY_1`, `CRON_SECRET`, `DAV_SYNC_TOKEN`, `CLERK_SECRET_KEY`, `CLERK_WEBHOOK_SECRET`, `PUSH_WEBHOOK_SECRET`, Turnstile secret). But service-role *code paths* are bundled to ~25 client files via `createServiceClient` in `src/lib/supabase.ts:53-67` (no `server-only`); only `inventarioService.ts` marks `import 'server-only'`.
5. **Data RLS risk registered** (P2.1): wide anon policies on WhatsApp/notifications/timeline/presupuestos; `historia_clinica_ortodoncia`, `user_preferences`, `o_leary` RLS disabled — anon key is public-by-design (pinned in the bundle).
6. **Hard-coded superuser / fail-open auth:** `src/lib/calendarAuth.ts:49`, `src/lib/inventoryAuth.ts:18` + bypass-on-error semantics.
7. **Good — no action:** Clerk provider/redirect flow, cron/push secret checks, calendar Phase-0 anon revocation, contacts Clerk-token RLS bridge, Sw strategy (SW.version bump in-push for a rolled release plan).

**Bottom line:** the app has real Clerk enforcement on *pages* (middleware redirects + 47 guarded routes), but the *defense-in-depth boundary* (default-deny API, RLS-enforced data) is missing. P0.1–P0.3 close the largest real-world attack surface with minimal code changes and can be executed with zero UI changes, so they are safe to enable for live users in one maintenance window.
